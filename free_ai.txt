Git-Up — Free AI Provider Integration Implementation Brief

Objective

Enhance Git-Up's existing AI configuration system by adding a zero-API-key free AI provider option while preserving the existing Custom API / OpenAI-compatible provider system exactly as it currently works.

The new feature must feel native to the existing Git-Up UI and must not break, replace, reset, migrate, or otherwise interfere with users who already configured a custom API.

The primary free-provider implementation should use Puter.js.

Puter currently supports browser-side AI through puter.ai.chat() and does not require the Git-Up developer to expose an API key. Users authenticate with Puter and their usage is handled through Puter's user-pays model.

Core Product Principle

Treat AI configuration as two independent modes:

Mode A — Custom API

This is the existing functionality.

Examples:

OpenRouter

OpenAI-compatible endpoints

Ollama/local endpoint

Custom providers

User-entered Base URL

User-entered API key

User-entered model

Do not rewrite this architecture unless absolutely necessary.

Existing stored configuration, request logic, validation, testing, model selection, and persistence must continue working exactly as before.

Mode B — Git-Up Free AI

New provider powered by Puter.js.

Characteristics:

No API key field required.

User can activate it from the existing AI settings interface.

User may need to authenticate with Puter.

Git-Up sends AI requests through Puter's browser SDK.

The user's existing Custom API credentials remain untouched.

Switching back to Custom API immediately restores the previous configuration.

Puter.js Integration

Integrate Puter using the official JavaScript SDK.

Puter supports browser usage through:

<script src="https://js.puter.com/v2/"></script>

and AI requests through:

puter.ai.chat(prompt)

It also supports specifying models and other chat options.

If the project is already using a package-based framework, prefer the appropriate package integration rather than adding a second unrelated loading strategy.

Avoid loading Puter repeatedly.

Initialize it once through a dedicated adapter/module.

Example conceptual architecture:

src/
  ai/
    ai-provider.js
    custom-api-provider.js
    puter-provider.js
    ai-service.js

If the current project has a different structure, follow its existing architecture instead of forcing this exact folder layout.

Create an AI Provider Adapter

Centralize all AI calls behind one service.

For example:

async function generateAI(request) {
  const provider = getActiveProvider();

  if (provider === "puter") {
    return puterProvider.generate(request);
  }

  if (provider === "custom") {
    return customApiProvider.generate(request);
  }

  throw new Error("No AI provider configured");
}

The rest of Git-Up should call:

generateAI(...)

rather than directly calling:

fetch(...)

or:

puter.ai.chat(...)

throughout the application.

This makes the provider switch transparent to the rest of the product.

Request Compatibility Layer

The existing Custom API implementation may already expect a specific request structure.

Do not force Puter to mimic the HTTP implementation internally.

Instead, normalize the application's logical AI request.

For example:

{
  messages,
  systemPrompt,
  model,
  temperature,
  maxTokens
}

Then:

Custom provider

Translate the normalized request to the existing HTTP API format.

Puter provider

Translate the same logical request into:

puter.ai.chat(messages, options)

or the appropriate supported Puter request structure.

Puter's chat() API supports both a prompt string and message arrays, making it suitable for preserving conversational/system-context behavior where applicable.

Do not change prompt content unless required for compatibility.

Model Strategy

Do not expose the entire Puter model catalog immediately.

For the first implementation, define one sensible default model that is compatible with Git-Up's workload.

Prefer making it configurable internally:

const PUTER_DEFAULT_MODEL = "...";

rather than scattering the model name across the UI.

Puter currently exposes many providers/models and supports model selection through puter.ai.chat() options.

The UI can initially show:

Git-Up Free AI
Recommended model

rather than forcing users to understand provider/model infrastructure.

Important Security Rule

Never introduce a shared secret API key into the frontend.

Do NOT implement:

const FREE_API_KEY = "xxxxx";

inside public JavaScript.

Do NOT commit a provider secret to:

source code

.env values exposed to the browser

localStorage

public configuration

GitHub Pages assets

The Puter integration should rely on its intended browser SDK/authentication model instead. Puter explicitly documents direct browser-side AI access without requiring the app developer to provide an API key.

Error Handling / Fallback

Do not silently switch providers.

Example:

Custom API fails:

Custom API request failed.

[ Retry ]
[ Switch to Free AI ]

This is better than silently moving a user from their chosen API to another provider.

Similarly, if Puter fails:

Free AI is temporarily unavailable.

[ Retry ]
[ Use Custom API ]

Provider changes must always be user-controlled.

Existing Configuration Migration

Before implementing anything, inspect the current application to determine:

where API settings are stored

how active provider is determined

how connection status is calculated

how AI requests are sent

how model selection works

how settings are loaded on startup

which UI component owns the current API modal/panel

whether AI configuration currently exists in localStorage, IndexedDB, URL state, or another system

Do not guess these structures.

Extend them.

If the current configuration is something like:

{
  baseUrl,
  apiKey,
  model
}

do not destructively change it.

Instead evolve it safely toward something like:

{
  activeProvider: "custom",
  custom: {
    baseUrl,
    apiKey,
    model
  },
  puter: {
    connected: false
  }
}

Use the actual application's existing schema and migration conventions.

Git-Up Free AI appears as a second provider.

Future-Proof Architecture

Design this so another provider can later be added easily:

AI Service
   │
   ├── Custom API Provider
   ├── Puter Provider
   ├── Future Provider
   └── Future Local Provider

The rest of Git-Up should not care which provider is active.

It should simply request:

generateAI(request)

The provider layer decides how the request is executed.

This will make future integrations much safer and easier.

Final Implementation Instruction to the Coding Agent

Before writing code, inspect the existing AI configuration implementation and identify the smallest safe integration points.

Then implement Puter as an additional provider without rewriting the existing Custom API system.

The priority order is:

1. Preserve existing functionality
→ 2. Add provider abstraction
→ 3. Add Puter
→ 4. Add UI CTA
→ 5. Add topbar status
→ 6. Add connection/testing states
→ 7. Regression-test both providers

Do not remove or rename existing settings keys unless a backward-compatible migration is implemented.

Do not replace the current Custom API implementation with Puter.

Do not hard-code a shared AI API key.

Do not silently switch providers after an error.

The finished experience should feel like Git-Up simply gained a new built-in AI option, not like the existing AI system was replaced.
